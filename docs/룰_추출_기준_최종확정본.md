## Stage A — gate_keywords 최종 기준

### type 3분류

| type | 정의 | 처리 |
|---|---|---|
| DISEASE | 질환명 (당뇨, 고혈압 등) | 의료 목적 맥락 확인 필요 |
| PROHIBITED_ACTION | 금지 행위 표현 (진단, 처방, 치료 등) | FAIL 후보 생성 |
| DOCTOR_REPLACEMENT | 의사 대체 표현 (전문의 없이, AI가 판단 등) | FAIL 후보 생성, 무조건 FAIL_CONFIRMED 대상 |

> **판별 기준 (2026-08-14 추가)** — 위 표는 "무엇인지 정의"만 있고 **어떻게 구분하는지 기준이
> 없었다.** 실전 문서 투입 중 LLM이 type을 거의 전부 PROHIBITED_ACTION으로 발급하는 편향이
> 관측됐는데, 원인이 이 공백이었다(프롬프트가 참조할 판별 근거가 없었음). 판별은 **품사**
> 기준이다 — 명사가 그대로 키워드면 DISEASE, 행위를 가리키면 PROHIBITED_ACTION, 의사
> 대체를 명시하면 DOCTOR_REPLACEMENT. 조문에서 뽑히는 키워드는 대부분 질병명·생체지표
> (DISEASE)이므로, "PROHIBITED_ACTION만 반복해서 쓰지 말 것"을 프롬프트에 명시해 교정했다
> (`extract_a.py`, db_구축_설계서.md §3.2 동기화).

### weight 척도 1~5 (확정)

| weight | 의미 | 법적 근거 | 예시 키워드 |
|---|---|---|---|
| 5 | 고위해도 직접 해당 + 의료행위 명시 | 지침서-0091-03 Ⅲ.2.가·나 — 고위해도 5요소: ①생체적합성 문제 ②침습적 ③오작동 시 상해 ④위급상황 탐지 ⑤기기 통제·변경 | "진단", "치료", "삽입", "무호흡 측정", "의료기기 제어" |
| 4 | 의료 목적 강하게 암시 (단독 FAIL 후보) | 의료기기법(법률 제21263호) 제2조제1항 — 질병의 진단·치료·경감·처치·예방, 상해·장애 보정 | "암 예측", "부정맥", "당뇨 진단", "상해 보정" |
| 3 | 의료 맥락 시 위험, 웰니스 맥락 시 허용 가능 | 지침서-0091-03 Ⅳ.2.가(만성질환 현상 관리용) — 피드백·치료법 제공 여부가 경계 | "혈압 관리", "수면 무호흡", "혈당 모니터", "콜레스테롤" |
| 2 | 경계선 키워드 (웰니스 가능성 있음) | 지침서-0091-03 Ⅲ.2.다(저위해도) — 질병 언급 없는 측정·모니터링 | "심박수", "산소포화도", "체지방", "스트레스 지수" |
| 1 | 웰니스 키워드 (참고용, PASS 가능성 높음) | 지침서-0091-03 Ⅲ.가 + Ⅳ.1(일상건강관리용) — 체중, 피트니스, 수면 관리 등 | "수면", "체중", "운동", "칼로리", "스트레스 관리" |

> 소수점 없음. weight는 정수 1~5만 사용.

### 고위해도 5요소 상세 (지침서-0091-03 Ⅲ.2.가·나)

weight=5, FAIL_CONFIRMED 판정의 핵심 근거. 아래 5가지 중 하나라도 해당하면 고위해도로 보고 개인용 건강관리제품(웰니스)이 아닌 의료기기로 판단한다.

| 순번 | 요소 | 정의 | 예시 |
|---|---|---|---|
| ① | 생체적합성 문제 야기 | 제품에 쓰인 소재·물질이 인체에 접촉해 부작용(피부병 등)을 일으킬 우려가 있는지 여부 | 웨어러블 장치에 쓰인 특수 소재가 피부병 등 문제를 발생시킬 우려가 있는 경우 |
| ② | 침습적(invasive) | 신체 내부에 삽입되거나 피부·점막을 뚫고 들어가는지 여부 | 생체신호 수집을 위해 장시간 안구 등과 접촉하는 제품, 체내에 삽입해 생체현상을 측정하는 장치, 혈액 채취를 위해 피부를 침투하는 제품 |
| ③ | 오작동 시 상해·질병 유발 | 사용 의도대로 작동하지 않을 경우 사용자에게 상해·질병이 발생할 우려가 있는지 여부 | 장치의 전기적 특성으로 이상 징후 우려가 있는 제품, 수면무호흡 등을 측정하는 수면 평가 장치 |
| ④ | 위급상황 탐지 | 심정지·사망 등 위급한 상황을 탐지하는 기능이 있는지 여부 | 심정지 탐지 기능이 있는 제품, 무호흡 감지 알람 기능이 있는 제품 |
| ⑤ | 기기 기능·특성 통제·변경 | 다른 의료기기의 기능이나 작동 특성을 통제·제어·변경하는지 여부 | 의료기기를 통제·제어하는 기능을 수행할 수 있는 제품 |

> 위해도 판단요소(무엇을 볼 것인가) 자체는 지침서-0091-03 Ⅲ.2.가에, 고위해도 해당 시 처리(개인용 건강관리제품 아님으로 판단)는 Ⅲ.2.나에 규정. 5요소 중 하나라도 해당하면 즉시 고위해도 → weight=5 / FAIL_CONFIRMED 후보.

### FAIL_CONFIRMED 지정 기준 (확정)

verdict = FAIL_CONFIRMED로 직접 지정하는 조건 (관리자 최종 확정, LLM 판단 금지):

| 조건 | 판단 근거 | 예시 |
|---|---|---|
| 고위해도 5가지 중 하나라도 해당 | 지침서-0091-03 Ⅲ.2.가·나 | 체내 삽입, 위급상황 탐지(무호흡), 의료기기 통제, 오작동 시 상해 |
| 의료기기 정의 4가지 목적 명시 | 의료기기법 제2조제1항 | "질병 진단", "치료", "경감", "처치", "예방", "상해 보정", "구조·기능 변형" |
| type = DOCTOR_REPLACEMENT | 의사 진단·처방 대체는 무조건 의료행위 | "AI가 진단합니다", "처방 추천", "의사 상담 대체" |
| weight = 5 AND type = DISEASE | 위해도 최고 + 질병 직접 언급 | "암 진단", "심근경색 예측", "당뇨 치료 보조" |

**CONTEXT_CHECK 전환 조건** (FAIL_CONFIRMED → 하향 가능): weight 3~4이더라도 사용목적 표현이 "건강한 생활방식·습관 유도"에 한정되고 치료법·피드백을 제공하지 않으면 관리자 판단으로 CONTEXT_CHECK로 낮출 수 있음. 근거: 지침서-0091-03 Ⅲ.나(의사결정 흐름도) + Ⅳ.2.나(만성질환 의료정보 제공용) 예외 조항.

### 신호어

- FAIL: "해당한다", "의료기기로 본다", "고위해도"
- PASS: "해당하지 않는다", "저위해도", "개인용건강관리제품"
- CONDITIONAL: "단,", "다만,", "경우에 한하여"

### 키워드 분류 체계(keyword_category) 및 위해도 메타데이터 관리 방식 (2026-07-20 동기화)

> 아래 두 항목은 db_구축_설계서.md에는 2026-07-05에 이미 결정·반영됐으나 본 문서(룰 추출 기준)에는 누락돼 있던 내용이라 동기화한다.

**keyword_category — type과는 별개의 축, "의료행위 단계" 구분용**

gate_keywords의 `type`(DISEASE/PROHIBITED_ACTION/DOCTOR_REPLACEMENT)과 별개로, 키워드가 어느 의료행위 단계에 해당하는지를 나타내는 `keyword_category` 필드를 둔다. 의료기기법 제2조제1항의 목적 리스트(진단·치료·경감·처치·예방·상해 및 장애의 보정)를 아래처럼 2단계로 묶어 매핑한다.

| keyword_category | 정의 | 의료기기법 제2조 대응 목적 | 예시 키워드 |
|---|---|---|---|
| 진단단계 (DIAGNOSIS) | 질병의 유무·정도를 판별하는 단계 | "질병의 진단" | "혈당 진단", "암 검사", "부정맥 진단", "질환 여부 판별" |
| 치료단계 (TREATMENT) | 처치·개선·예방을 지시·유도하는 단계 (치료·경감·처치·예방·상해 및 장애의 보정을 하나로 포괄) | "치료·경감·처치·예방", "상해·장애의 보정" | "약물추천", "처치안내", "증상 완화 유도", "재활 보정 안내" |
| 데이터유형 (DATA_TYPE) | 특정 생체지표·병명 자체가 키워드로 쓰이는 경우 (단계 구분과 무관) | — (데이터 자체가 키워드) | "혈당", "혈압", "심전도", "당뇨" |
| 기타 (OTHER) | 위 세 가지에 해당하지 않는 경우 | — | — |

> **치료단계를 5개 목적(치료·경감·처치·예방·상해보정)으로 세분화하지 않고 하나로 묶은 이유**: 이 5개 목적을 서로 다른 카테고리로 나눌 만큼 유의미한 규제 차이가 없고(Stage B에서 민감정보·임상진료를 별도 축으로 두지 않은 것과 같은 논리), "질병 판별(진단)"과 "판별 이후의 개입(치료·경감·처치·예방·보정)"이라는 큰 성격 차이만 구분하면 충분하기 때문.
>
> `type`(무엇을 하는 키워드인지: 질환명/금지행위/의사대체)과 `keyword_category`(어느 단계인지: 진단/치료/데이터유형/기타)는 서로 직교하는 별도 축이며, **위험도(weight) 산출에는 `type`+`weight`만 사용하고 `keyword_category`는 관리자 화면 분류·검수 편의용으로만 쓴다.** 진단단계와 치료단계 사이에 weight 차등을 두지 않는 이유: 의료기기법 제2조는 진단·치료·경감·처치·예방을 동일 선상에 나열할 뿐 그중 하나가 더 위험하다고 규정하지 않으며, 현재 Stage A weight 표에서도 이 다섯 목적은 이미 동일하게 weight=4/FAIL_CONFIRMED 대상으로 처리되고 있어 추가 차등을 줄 법적 근거가 없다. 스키마 정의는 db_구축_설계서.md §3.2 참조.

**위해도 등급의 DB 외부 메타데이터 분리 (risk_metadata)**

고위해도 5요소 목록, weight 척도, FAIL_CONFIRMED 조건 등 "위해도 판단 기준" 자체는 gate_keywords 테이블의 컬럼값이 아니라 별도 설정 파일(`risk_metadata.json`) 또는 관리자 설정 테이블(`risk_config`)로 분리 관리한다. 의료기기 판단 가이드가 개정될 때 DB 전체를 재구축하지 않고 메타데이터만 갱신하면 되도록 하기 위함. 스키마 정의는 db_구축_설계서.md §3.2.1(`risk_metadata`) 참조 — 본 문서(위 weight 척도·고위해도 5요소·FAIL_CONFIRMED 표)는 그 메타데이터의 "내용"에 해당하고, §3.2.1은 그것을 "어디에 저장하는지"에 해당한다.

> `data_type_focus`(gate_keywords, 영상/텍스트/수치/해당없음 — 입력 포맷 참고용 태그)는 위험도 판단에 전혀 사용하지 않는다. 위험도는 오직 weight(Stage A, 본 절) + gate_matrix.data_type(Stage B)만으로 산출한다 (2026-07-05 결정, db_구축_설계서.md §3.2). 아래 "잔여 미결정 사항" 참조.

## Stage B — gate_matrix 최종 기준

### data_type 2분류 정의·경계 (1차 구축 범위, 2026-07-12 확정)

| data_type | 정의 | 경계 기준 | 근거 |
|---|---|---|---|
| 라이프스타일 | 진단·치료 피드백 없이 식단·운동·수면 등을 자가관리하도록 돕는 데이터 | "환자 맞춤형 진단·치료법 제공" 여부 | 모바일앱지침 Ⅲ.3.2 |
| 생체지표 | 혈당·혈압·심전도·산소포화도 등 측정값. 그 자체로 개인정보보호법상 민감정보에 해당하는 것으로 간주 | 표시·저장만=웰니스 / 분석 후 진단·치료 피드백=의료기기 | 모바일앱지침 Ⅲ.2.2~4, 웰니스판단기준(0091-03) Ⅳ.3, 개인정보보호법 제23조제1항 |

> **민감정보를 별도 data_type으로 두지 않은 이유**: 민감정보(유전정보·건강정보·성생활정보 등)를 별도로 세분화하기엔 판단 기준이 모호하고, 실제로 이 프로젝트가 다루는 민감정보는 대부분 생체지표(건강정보)이므로 별도 축을 두지 않고 생체지표에 포함되는 개념으로 처리한다. 유형별로 규제 수준이 명확히 다르게 적용되는 것도 아니다.
>
> **임상·진료를 제외한 이유**: 세분화 자체는 의미가 있으나 포함할 경우 구축 난이도가 크게 상승하고, 현재 관련 데이터도 부재하다. 1차 구축에서는 제외하고, 2차 구축 단계에서 별도 data_type으로 재도입 예정.

> **function_type 트리 적용 제외 영역**: 모바일앱지침 Ⅲ.2.1(의료기기 무선 제어), Ⅲ.2.3~4(전극·센서로 자체 측정)는 "데이터로 뭘 하는가"가 아니라 "기기를 제어·통제하거나 그 자체가 측정기기로 동작하는가"의 문제라 Stage A(gate_keywords, 고위해도 5요소 중 ⑤ 기기 통제·변경)에서 이미 걸러진다. Ⅲ.3.1(일반 의료정보 제공)·Ⅲ.3.4(화상 통신)는 사용자 데이터를 다루지 않는 정보열람·통신 기능이라 애초에 data_type×function_type 프레임 대상이 아니다. 이 5개 세부유형은 function_type 판별 트리에 넣지 않는다.

**경계 케이스 처리 원칙 (RAG 미사용, 3단계 결정론적 처리)**

1. **우선순위 규칙**: 하나의 앱에 여러 function_type 신호가 섞여 있으면 더 위해도가 높은 쪽(수치예측·진단 > 비교·추이분석 > 단순기록)으로 분류한다. 기존 verdict 우선순위(FAIL > CONDITIONAL > PASS) 패턴과 동일한 원리.
2. **디시전 트리 세분화**: 그래도 애매하면 위 Q1/Q2 분기점에 부록2 회신사례 같은 추가 판례를 세부 하위질문으로 넣어 트리를 더 좁힌다.
3. **CONDITIONAL/관리자 검수 폴백**: 위 두 단계로도 해결 안 되는 잔여 케이스는 CONDITIONAL로 분류하고 LangGraph의 human_review interrupt 노드로 넘겨 관리자가 최종 판단한다.

### data_type × function_type PASS/FAIL/CONDITIONAL 매핑 (6칸 확정, 즉시 시드데이터 적재 가능)

> **(2026-07-26 추가) acquire_method·회피 방향 필드 복원**: gate_matrix에 acquire_method(획득방법: 수동입력/기기연동/OS연동)와 avoidance_redesign/avoidance_certification(회피 방향 2가지 안내) 필드가 복원됨. 위 6칸 매핑표는 data_type×function_type 축만 다루므로 표 자체는 변경 없음 — acquire_method는 매트릭스 축이 아니라 "생체지표+기기연동+침습적 키워드" 조합의 하드체크 오버라이드 전용이고, avoidance_*는 verdict=FAIL row에만 채우는 보조 안내 필드. 상세 정의·근거는 db_구축_설계서.md §3.2 참조.

## (구) Stage D — bm_mapping — **폐지 (2026-07-20), VIEW로 전환**

> ⚠️ 아래 내용은 과거 제안 단계 기록으로만 남긴다. **최신 정의는 db_구축_설계서.md V3.0 §3.6을 참조.** bm_mapping은 법령·고시를 LLM이 추출하는 룰이 아니라 competitors 데이터를 실시간 집계하는 SQL VIEW로 확정되었으므로, Stage A~C와 같은 "룰 추출 기준"의 대상이 아니게 됨. 별도 적재·검수 파이프라인도 없음.

### frequency_score 산출 (제안 → db_구축_설계서.md §3.6에서 SQL VIEW로 확정)

```
-- 제안 당시 로직 (그대로 채택됨)
frequency_score = competitors 테이블에서 동일 (category, target, service_type, bm_pattern) 조합을 가진 경쟁사 수 (자동 집계)
```

### precedent_level 수치 기준 (제안 → 확정, 국내/해외 분리로 완전 자동화)

| precedent_level | 조건 (db_구축_설계서.md §3.6 최종본) |
|---|---|
| 많음 | 국내(country='한국') frequency_score ≥ 5 |
| 중간 | 3 ≤ 국내 frequency_score < 5 |
| 적음 | 1 ≤ 국내 frequency_score < 3 |
| 가능 | 국내 frequency_score = 0, 해외 포함 전체(frequency_score_global) ≥ 1 |
| 어려움 | 국내외 모두 0 |

> **"규제 장벽 존재" 판단 기준 미확정 문제는 해소됨**: 당시엔 frequency_score=0일 때 "가능"과 "어려움"을 가르는 기준으로 "규제 장벽 존재 여부"라는, 데이터로 확인할 수 없는 정성적 판단이 필요했음. db_구축_설계서.md §3.6에서 frequency_score를 국내(frequency_score)/전체(frequency_score_global) 두 값으로 분리하면서, "국내 0 + 해외 존재=가능", "국내외 모두 0=어려움"으로 전적으로 데이터 기반 자동 판정이 가능해짐 — 규제 장벽을 사람이 판단할 필요가 없어짐.
>
> **여전히 미확정인 것**: 임계값 자체(많음≥5, 중간3~4, 적음1~2)는 통계적·법적 근거 없이 정한 예시값이며, Business Model Navigator 12개 패턴 서브셋과 마찬가지로 팀 회의 확정 필요 (db_구축_설계서.md §8.2).

### 최신 정의 (db_구축_설계서.md V3.0 §3.6 그대로 발췌, 2026-07-20)

```sql
CREATE VIEW bm_mapping AS
SELECT
  category_1,
  category_2,
  target,
  service_type,
  bm_pattern,
  COUNT(*) FILTER (WHERE country = '한국') AS frequency_score,
  COUNT(*) AS frequency_score_global,
  CASE
    WHEN COUNT(*) FILTER (WHERE country = '한국') >= 5 THEN '많음'
    WHEN COUNT(*) FILTER (WHERE country = '한국') >= 3 THEN '중간'
    WHEN COUNT(*) FILTER (WHERE country = '한국') >= 1 THEN '적음'
    WHEN COUNT(*) > 0 THEN '가능'          -- 국내 0, 해외 사례는 존재
    ELSE '어려움'                          -- 국내외 모두 0
  END AS precedent_level,
  STRING_AGG(competitor_id::text, ',') AS contributing_competitor_ids
FROM competitors
WHERE category_1 IS NOT NULL AND category_2 IS NOT NULL AND target IS NOT NULL AND service_type IS NOT NULL AND bm_pattern IS NOT NULL
GROUP BY category_1, category_2, target, service_type, bm_pattern;
```

| 출력 컬럼 | 설명 |
|---|---|
| category_1 | 질병축(7종) — 수면/정신건강/운동/식단/만성질환/여성건강/미용 (2026-07-20 갱신: 기존 5종 category → category_1/category_2 2축 교체, 이후 유전자 제외로 8종→7종 조정) |
| category_2 | 기능축(4종) — 정보제공/데이터기록관리/매칭연결/개입치료 |
| target | 타겟 사용자군 |
| service_type | 서비스 형태 |
| bm_pattern | Business Model Navigator 패턴 (닫힌 enum, 후보 12개는 §8.2) |
| frequency_score | 국내(country='한국') 경쟁사 수 기준 빈도 |
| frequency_score_global | 국내+해외 전체 빈도 — precedent_level '가능' 판정 전용 |
| precedent_level | 많음/중간/적음/가능/어려움, 100% 자동 산출 |
| contributing_competitor_ids | 집계에 포함된 competitor_id 목록 — 리포트 근거 표시용 |

> category_1의 "만성질환"은 data_type(라이프스타일/생체지표, GATE 규제 판단용) 2분류에서 임상·진료를 1차 구축 제외한 것과 상충하지 않음 — category_1/2는 시장 분류 전용 축, data_type은 규제 분류 전용 축으로 서로 별개(db_구축_설계서.md §3.5 참조).

**evidence_id는 MVP 범위 제외**: 가격·전환율 등 정량 근거는 VIEW로 표현 불가능한 수동 큐레이션 정보라 1차 구축에서 두지 않음. 필요해지면 (category_1, category_2, target, service_type, bm_pattern)을 참조키로 하는 별도 소형 테이블(`bm_evidence_note`)을 추가해 이 VIEW와 애플리케이션 레벨에서 LEFT JOIN.

산출 절차: 별도 파이프라인 없음 — competitors에 데이터가 쌓이는 즉시 이 VIEW 조회 결과에 반영됨. category_1/category_2/target/service_type으로 필터링 후 frequency_score 상위 2개를 추천안으로 사용.
