# 검진 데이터 입력 화면 명세서 (프론트 와이어프레임 수정용)

> 담당: 1번(Gate/규제 위험도 판정) 정리 · 대상: 프론트 공유용
> 현재 Figma 화면(첨부된 스크린샷, 변경 전) 기준으로 실제 API가 받는 필드와 대조,
> 빠졌거나 안 맞는 부분을 정리했다. 화면 구성/UI는 프론트 재량, 여기선 **어떤
> 값을 어떤 형식으로 넘겨야 하는지**만 다룬다.

## 전체 흐름 (스텝 순서 제안)

1. **서비스 설명** (기존 STEP 1) — 그대로 유지
2. **카테고리 확인** ⚠️ **신규 화면 필요** — 지금 와이어프레임에 아예 없음
3. **주요 타겟과 수집할 데이터** (기존 STEP 2-3) — 항목 재정비 필요
4. **수집 방법 및 활용 목적** (기존 STEP 4-6) — 항목 재정비 필요

---

## 2. 카테고리 확인 (신규)

서비스 설명 입력 다음 화면으로 넣어야 한다 — 카테고리는 시장성/BM API가 조회
키로 쓰는 필수값이라 사용자가 직접 확인/확정해야 한다.

**동작**: STEP 1에서 "다음 단계" 클릭 시 `POST /api/v1/category-classifier/predict`
(`{service_description}`만 전달)를 호출 → 이 화면에서 추천값을 보여주고, 사용자가
그대로 쓰거나 목록에서 다른 값으로 바꾸거나 수기 입력 가능.

**category_1** (질병/분야축, 7종 중 1개 선택) — 라디오 버튼 형태 추천:
`수면` / `정신건강` / `운동` / `식단` / `만성질환` / `여성건강` / `미용`

**category_2** (기능축, 4종 중 1개 선택):
`정보제공` / `데이터기록관리` / `매칭연결` / `개입치료`

두 값 다 이 목록 밖의 문자열이 들어가면 시장성/BM 매칭이 항상 실패
(`insufficient_data`)한다 — 수기 입력을 허용하더라도 이 목록에서 벗어나면
경고를 보여주는 게 안전하다.

## 3. 주요 타겟과 수집할 데이터

### 3-1. 주요 타겟 — ⚠️ 필드가 하나 더 필요함

지금 화면(연령대 + 특성·생활군 다중선택)은 `target_users`(자유 텍스트 리스트,
리포트 표시용)로만 쓰인다. **시장성/BM API가 실제로 매칭에 쓰는 건 별도의
`target`(단일 문자열) 필드인데, 지금 화면엔 이걸 받는 입력이 없다.**

- `target_users`: 지금 화면 그대로(다중선택 태그) → 리스트로 전송, 매칭에는
  안 쓰이고 표시용
- `target`: **경쟁사 DB에 저장된 형식과 맞아야 정밀 매칭이 시도된다** — 실제
  시드 데이터 예시: `"다이어터, 20~40대"`, `"당뇨환자, 식단관리"`,
  `"가임기 여성"` 같은 짧은 콤마구분 문구. 선택한 태그들을 콤마로 이어붙여서
  이 필드에 같이 넣어주는 걸 추천(예: "다이어터" + "20~40대" 선택 →
  `target: "다이어터, 20~40대"`).
- **안 채워도 에러는 아니다** — `target`이 없으면 시장성/BM API가 자동으로
  카테고리만으로 완화 조회한다(`relaxed_category_only`). 다만 정밀도가
  떨어지니 가능하면 채우는 걸 권장.

### 3-2. 수집할 데이터 — 카탈로그(`data_sensitivity`, 18개) 기준으로 재정비

각 버튼은 `item_code`를 값으로 가지고 있어야 한다(`item_code`가 없으면 그
항목은 규제위험도 계산에서 조용히 빠진다). 아래가 실제 DB에 있는 전체 18개
항목 — **이 목록에 없는 이름(활동량/기분 기록/체성분/심리 상담 기록 등)은
`item_code`가 없어서 화면엔 보여도 점수 계산에 반영이 안 된다.**

| 그룹(UI) | item_code | 항목명 | 민감도 |
|---|---|---|---|
| 라이프스타일 | `lifestyle_001` | 걸음수 | 낮음 |
| 라이프스타일 | `lifestyle_002` | 수면 시간 | 낮음 |
| 라이프스타일 | `lifestyle_003` | 식단 기록 | 낮음 |
| 라이프스타일 | `lifestyle_004` | 운동 기록 | 낮음 |
| 라이프스타일 | `lifestyle_005` | 스트레스 기록 | 낮음 |
| 생체 지표 | `biometric_001` | 심박수 | 중간 |
| 생체 지표 | `biometric_002` | 혈압 | 중간 |
| 생체 지표 | `biometric_003` | 체중·BMI | 중간 |
| 생체 지표 | `biometric_004` | 체온 | 중간 |
| 생체 지표 | `biometric_005` | 산소포화도 | 중간 |
| 민감 정보 | `sensitive_001` | **혈당** | 높음 |
| 민감 정보 | `sensitive_002` | 유전자 정보 | 높음 |
| 민감 정보 | `sensitive_003` | 생리주기·임신 | 높음 |
| 민감 정보 | `sensitive_004` | 복용 약물 | 높음 |
| 민감 정보 | `sensitive_005` | 과거 병력·진단 이력 | 높음 |
| 행동 데이터 | `behavior_001` | 앱 체류시간 | 낮음 |
| 행동 데이터 | `behavior_002` | 구매 이력 | 중간 |
| 행동 데이터 | `behavior_003` | 위치 정보 | 중간(별도 동의 필요) |

**지금 화면과 다른 부분 — 수정 필요**:
- ⚠️ **혈당이 "생체 지표"가 아니라 "민감 정보" 그룹이다**(`sensitive_001`,
  민감도 높음). 지금 화면은 혈당을 생체지표 그룹에 넣어놨는데, 그룹을
  옮겨야 한다.
- "체중" → "체중·BMI"로 라벨 변경(`biometric_003`)
- "식단 사진" → "식단 기록"으로 변경(`lifestyle_003`) — 사진이라는 미디어
  타입은 `data_type` 필드(별도, 아래 참고)로 표현하면 됨
- "활동량" → 카탈로그에 없음. "운동 기록"(`lifestyle_004`)으로 대체하거나,
  "활동량"을 정말 별도로 두고 싶으면 새 `item_code` 시딩이 필요(백엔드 팀
  확인 필요)
- "기분 기록" → 카탈로그에 없음. "스트레스 기록"(`lifestyle_005`)으로 대체
  추천
- "체성분" → 카탈로그에 없음(생체지표 판별 키워드로만 존재, 민감정보
  카탈로그엔 없음). 버튼에서 빼거나 새 `item_code` 시딩 필요
- "심리 상담 기록" → 카탈로그에 없음. 필요하면 새 `item_code` 시딩 필요
- "생리주기" → "생리주기·임신"으로 라벨 변경(`sensitive_003`)
- 생체 지표 그룹에 "체온"(`biometric_004`), "산소포화도"(`biometric_005`)
  버튼이 빠져있음 — 추가 필요
- "기타 - 직접 입력"은 유지 가능하지만, 수기 입력한 항목은 `item_code`가
  없어서 규제위험도 계산에서 빠진다는 걸 사용자에게 안내 문구로 알려주는
  게 좋음(예: "직접 입력한 항목은 위험도 자동 평가에서 제외될 수 있습니다")

각 항목을 선택하면 최종적으로 아래 형태로 전송된다(`data_type`은 값의
타입 — 사진이면 `image`, 숫자 기록이면 `numeric` 등, 화면엔 안 보여도 됨,
프론트가 항목별로 고정값 매핑):
```json
{"name": "혈당", "data_type": "numeric", "source": "...", "is_sensitive": true, "item_code": "sensitive_001"}
```

## 4. 데이터 수집 방법 (source) — ⚠️ 버튼 1개 부족

백엔드는 4개 값을 받는데 지금 화면엔 3개 선택지뿐이다:

| 화면 버튼(현재) | 매핑되는 값 | 문제 |
|---|---|---|
| 사용자 자가 입력 | `user_input` | OK |
| 웨어러블 연동 (HealthKit·Google Fit) | `os_sync`(OS연동) | 이름은 "웨어러블"인데 실제로는 OS연동 값임 |
| 병원·임상 데이터 (EMR·병원 DB) | `institution_sync`(기관연동) | OK (오탈자로 보이는 "모발일 DB"는 "병원 DB" 확인 필요) |
| — | `device_sync`(기기연동) | **버튼 자체가 없음** |

`device_sync`(기기 직접연동 — 제조사 API/블루투스로 기기와 직접 통신, 예:
CGM 제조사 앱 연동)는 `os_sync`(HealthKit/Google Fit 같은 OS 레이어 경유)와
**완전히 다른 값**이고, 침습적 기기(CGM 등) 하드체크 FAIL 판정이 바로 이
`device_sync` 값에 걸려 있다. 지금처럼 "웨어러블 연동" 버튼 하나로 뭉쳐서
`os_sync`로만 보내면, 실제 침습적 기기 연동 케이스가 **하드체크에 안
걸릴 수 있다** — 규제 위험도가 낮게 오판정될 위험.

**추천**: "웨어러블 연동" 버튼을 둘로 분리
- "기기 직접연동" (제조사 앱/기기 API로 직접 연결) → `device_sync`
- "OS 건강앱 연동" (HealthKit·Google Fit) → `os_sync`

"선택 안 함"은 필수 필드라 제출은 막고, 기본 미선택 상태로만 두면 됨.

## 5. 서비스 형태 (service_type)

이 필드도 시장성/BM 매칭 키로 쓰이는데, 실제 경쟁사 DB엔 "모바일 앱"/
"웹 서비스" 같은 큰 분류가 아니라 `"D2C구독"`, `"B2B(의료기관 대상 SaaS)"`,
`"앱단독+웨어러블 연동"` 같은 훨씬 세분화된 값이 들어있다. 지금 화면의
4개 선택지(선택 안함/모바일 앱/웹 서비스/웨어러블 기기)로는 거의 정확히
안 맞는다.

**이건 화면 문제라기보단 원래 설계가 그렇다** — `target`과 마찬가지로
`service_type`이 안 맞아도 에러가 아니라 카테고리만으로 완화 조회
(`relaxed_category_only`)되므로 지금 화면 그대로 둬도 기능은 정상 동작한다.
정밀 매칭 확률을 높이고 싶으면 선택지를 competitors 시드 스타일에 가깝게
넓히는 걸 고려할 수 있지만, 지금 범위에선 필수 아님(참고만 해두기).

## 6. 데이터로 무엇을 하나요? (service_actions)

| 화면 버튼 | 값 |
|---|---|
| 단순 기록·저장 | `record` |
| 비교·추이 분석 | `visualize_trend` |
| 위험 알림 | `alert` |
| 수치 예측·진단 | `predict` |

⚠️ **"위험 알림"과 "수치 예측·진단"은 내부적으로 완전히 같은 등급으로
처리된다** — 둘 다 GATE 매트릭스에서 가장 엄격한 "수치예측·진단" 등급으로
분류된다. 지금 화면엔 "수치 예측·진단" 아래에만 "의료기기 해당 가능성이
높아져 GATE 판정 및 규제 위험도가 엄격하게 산출됩니다" 경고가 붙어있는데,
"위험 알림"에도 똑같은 경고를 붙이는 게 맞다(사용자가 오해하지 않도록).

## 요약 — 우선순위별 액션 아이템

**🔴 반드시 반영**
1. 카테고리 확인 화면 신규 추가 (§2)
2. `target`(단일 문자열) 입력 누락 — 매칭 정밀도에 직접 영향 (§3-1)
3. 혈당을 민감정보 그룹으로 이동 (§3-2)
4. 수집 데이터 항목을 18개 카탈로그 기준으로 정리 — 카탈로그에 없는
   항목(활동량/기분 기록/체성분/심리 상담 기록)은 대체하거나 새 시딩 요청 (§3-2)
5. "웨어러블 연동" 버튼을 기기연동/OS연동으로 분리 — 침습 하드체크 정확도
   직결 (§4)

**🟡 하면 좋음**
6. "위험 알림"에도 "수치 예측·진단"과 같은 경고 문구 추가 (§6)
7. 체온/산소포화도 버튼 추가 (§3-2)

**🟢 참고만**
8. `service_type` 정밀 매칭은 지금 4개 선택지로는 거의 안 맞지만, 안 맞아도
   기능은 정상 동작(자동 완화) — 급하지 않음 (§5)
