# B. 판정 로직 (4개) — 🔵 **전부 런타임(판정엔진)에서 계산**

> 🔵 **4~7번은 모두 판정엔진(FastAPI팀) 구현 범위입니다.** 오프라인 파이프라인(Stage A/B/C)에 구현하지 마세요. 사용자 입력이 있어야 계산되는 값들입니다.

## 4. D×S 데이터확보 난이도 — 🔵 런타임 (§02 모듈)

`개별점수 = D × S` (곱), 복수 선택 시 **최댓값** 채택

| | 수동입력(1) | OS연동(2) | 기기연동(4) | 기관연동(10) |
|---|---|---|---|---|
| **라이프스타일(1)** | 1 🟢 | 2 🟢 | 4 🟡 | 10 🟡 |
| **생체지표(3)** | 3 🟢 | 6 🟡 | 12 🔴 | 30 🔴 |

| 총점 | 등급 |
|---|---|
| 1~3 | 🟢 쉬움 |
| 4~10 | 🟡 보통 |
| 12~30 | 🔴 어려움 |

## 5. privacy_score 산출표 — 🔵 런타임 (§01 모듈)

**입력**: 사용자가 아이디어 입력 Step2에서 선택한 **수집 데이터 항목** → `data_sensitivity.sensitivity_level` 조회

| sensitivity_level | privacy_score |
|---|---|
| 3 | 3 |
| 2 | 2 |
| 1 | 1 |
| 미포함 | 0 |

복수 항목 선택 시 **최댓값** 채택.

> ⚠️ **`correction_rules`에 저장하지 않습니다.** 같은 위험표현("불면증 진단")이라도 수집 데이터가 수면(level 1)이냐 복용약물(level 3)이냐에 따라 개인정보 위험이 달라야 하는데, 룰에 저장하면 값을 하나만 가질 수 있어 구조적으로 불가능합니다.
>
> **원칙**: 표현에서 결정되는 값(regulatory·advertising)은 룰에 저장하고, 사용자 입력에서 결정되는 값(privacy)은 런타임에 계산합니다. (db_구축_설계서 §3.3.2)

### ⚠️ 동의 요건은 action_templates로 이관

동의 언급 여부가 점수 산출에서 제외되면서, 별도 동의 요건을 안내할 곳이 액션밖에 없습니다. **아래 행은 `action_templates` 필수 시드입니다.**

| trigger_type | trigger_value | 안내 요지 |
|---|---|---|
| sensitivity_level | 3 | 개인정보보호법 제23조 **별도 동의** 필요. 일반 이용약관 동의·통합 동의로는 요건 미충족 |

이 행이 없으면 민감정보 수집 서비스에 동의 요건을 전혀 안내하지 못합니다.

## 6. 경쟁 포화도 → 시장현실성 매핑 — 🔵 런타임 (§03 모듈)

| 경쟁사 수(n) | 포화도 | **시장현실성 지표** |
|---|---|---|
| 0~2 | Opportunity | **높음** |
| 3~4 | Challenging | **중간** |
| 5 이상 | Saturated 후보 | **낮음** |
| 5 이상 + tier='플랫폼' 존재 | Saturated (확정) | **낮음** |

> ⚠️ **역관계 주의** — 포화도가 낮을수록 시장현실성은 높습니다. 구현·문구 작성 시 가장 헷갈리는 지점입니다.

**n을 세는 범위**는 **`db_구축_설계서 §6.4`의 4단계 완화 전략**을 따릅니다.

```
1) exact_match          : category_1 + category_2 + target + service_type 전부 일치
2) relaxed_service_type : service_type 조건 해제
3) relaxed_category_only: category_1 + category_2 만 일치
4) insufficient_data    : 위 3단계 모두 n=0
```

§04 BM 추천과 **동일한 전략을 공유**합니다.

## 7. 앱스토어 순위 → 국내 수요 등급 — 🔵 런타임 (§03 모듈)

| 해당 category_1 앱 중 최고 순위 | 판정 |
|---|---|
| 100위 이내 | 상위권 |
| 101~300위 | 중위권 |
| 300위 밖 또는 없음 | 낮음 |

> 건강·피트니스 카테고리 **무료 순위** 기준

> 데이터 수집(app_store_ranking 배치 크롤링)은 담당 E, 등급 매핑은 판정엔진입니다.

## 8. data_sensitivity.sensitivity_level

| level | 정의 | 예시 |
|---|---|---|
| 3 | 그 자체로 질병·치료·생식 이력이 드러남 | 복용약물, 과거병력, 심리상담기록, 유전자정보, 생리주기 |
| 2 | 신체 측정값이나 단독으로 질병 특정 어려움 | 심박수, 혈압, 혈당, 체중, 체성분 |
| 1 | 라이프스타일 | 걸음수, 수면시간, 식단사진, 활동량, 기분기록 |

> **level 구분은 "민감정보인가 아닌가"의 이분법이 아니라 재식별·피해 위험의 정도**입니다. 심박수도 개인정보보호법 제23조의 "건강에 관한 정보"로 민감정보에 해당할 여지가 있으므로, level 2를 "민감정보가 아님"으로 단정하지 마세요.

### ⚠️ `item_label`은 Step2 UI 옵션 문자열과 글자 단위로 일치해야 함

privacy_score가 런타임 계산이 되면서 **사용자가 고른 값으로 직접 조회**합니다. 따라서 `item_label`이 아이디어 입력 Step2의 UI 옵션 문자열과 **정확히 같아야** 합니다.

- "심박수" vs "심박 수" → 조회 실패
- 실패 시 해당 항목의 민감도가 **조용히 누락**됨 (에러가 안 남)

**착수 전 디자인 담당으로부터 확정된 옵션 목록을 받아 그대로 복사할 것.**

## 9. public_data_catalog.difficulty

| difficulty | 기준 |
|---|---|
| 1 | 로그인 없이 즉시 다운로드 또는 API 조회 가능 |
| 2 | 회원가입·신청 필요하나 승인이 자동이거나 간단 |

| 대역 | 용도 |
|---|---|
| 900~999 | GATE FAIL 관련 (최우선) |
| 700~899 | 규제위험도 높음 |

# E. 값 산출 완료, 팀 검토 대기 (1개)

**트렌드 기울기 임계값** — 산출 절차는 db_구축_설계서 §6.8 확정분 그대로 적용. 담당 C가
네이버클라우드플랫폼 Search Trend로 실제 20개 업종(성장 예상 10 / 정체·하락 예상 10)을
2025-08-03~2026-08-03 일간 단위로 조회해 아래 값을 산출(2026-08-04).

| axis_key | value | unit | 비고 |
|---|---|---|---|
| trend_slope_threshold | -0.151 | %/일 | 성장군 평균(-0.180)과 정체·하락군 평균(-0.121)의 중간값 |
| trend_growth_group_avg | -0.180 | %/일 | 성장 예상 10개 그룹 평균 |
| trend_decline_group_avg | -0.121 | %/일 | 정체·하락 예상 10개 그룹 평균 |
| trend_calc_last_run | 2026-08-04 | YYYY-MM-DD | 분기 1회 재계산 권장 |

> ⚠️ **팀 검토 필요**: 성장 예상 그룹이 정체·하락 예상 그룹보다 **더 크게 하락**한 것으로
> 나왔다 — 아래 산출 절차 [1]의 "성장/정체 라벨은 검색 트렌드가 아닌 외부 근거(시장 보고서·
> 투자 동향)로 붙일 것"이라는 전제 자체가 실제로 지켜졌는지, 혹은 성장/정체군 카테고리 선정
> 기준을 다시 봐야 하는지 팀 회의에서 확정 전까지는 이 값을 그대로 signal_config에 반영하지
> 말 것.

## 산출 절차

```
[1] 웰니스 인접 업종 20개 선정 (성장 10 / 정체·하락 10)
    ※ 성장/정체 라벨은 검색 트렌드가 아닌 외부 근거(시장 보고서·투자 동향)로 붙일 것
      트렌드로 라벨을 붙이면 순환논리가 됨
[2] 앵커 키워드 포함해 데이터랩 5회 호출
[3] 앵커 값 비율로 배치 간 스케일 보정
[4] 최소제곱법으로 각 업종 기울기 산출
[5] 두 그룹 기울기 분포의 교차점 = 임계값
[6] 성장 그룹 1사분위수로 검증
    → 교차점이 Q1보다 높으면 성장 업종 하위 25%를 놓치는 것이므로 하향 조정
```

## ⚠️ 호출 횟수는 4회가 아니라 **5회**

데이터랩은 한 호출에 검색어 그룹 5개까지 받는데, **앵커 키워드가 1칸을 차지**하므로 배치당 업종은 4개입니다.

```
배치1: [앵커, 업종A, 업종B, 업종C, 업종D]
배치2: [앵커, 업종E, 업종F, 업종G, 업종H]
배치3: [앵커, 업종I, 업종J, 업종K, 업종L]
배치4: [앵커, 업종M, 업종N, 업종O, 업종P]
배치5: [앵커, 업종Q, 업종R, 업종S, 업종T]

20개 업종 ÷ 4 = 5회
```

앵커 없이 5개씩 넣으면 4회지만, **데이터랩의 정규화는 한 호출 안에서만 유효**해서 배치마다 스케일이 리셋됩니다. 앵커 없이는 기울기 비교 자체가 불가능하므로 앵커는 필수이고, 따라서 5회입니다.

## 보완 조건 4가지

| # | 조건 | 이유 |
|---|---|---|
| ① | **앵커 키워드** | 배치 간 스케일 보정. 계절성 적고 검색량 안정적인 단어 선정 |
| ② | **24개월 수집** | 12개월만 보면 계절성과 성장 구분 불가. 전년 동월 대비를 보조 지표로 병행 |
| ③ | **R² ≥ 0.3** | 미달 시 "변동성 큼 — 판별 불가"로 처리, 급성장/하락 판정 부여 안 함 |
| ④ | **저검색량 제외** | 12개월 중 0이 3개월 이상이면 "데이터 부족" 처리 |

> ②가 특히 중요합니다. "다이어트"를 1월에 조사하면 급성장, 9월에 조사하면 하락으로 나옵니다. 같은 아이디어인데 리포트를 뽑은 달에 따라 판정이 뒤집히면 신뢰도 문제가 큽니다.
