## 1. 개요

### 1.1 이 문서의 범위

PREP은 세 개의 층으로 구성된다.

| 층 | 내용 | 소유 문서 |
|---|---|---|
| 1층 | DB에 무엇을 어떤 절차로 채워 넣는가 | db_구축_설계서.md |
| **2층** | **채워진 DB를 조회해 어떻게 판정하는가** | **본 문서** |
| **3층** | **판정 결과를 어떻게 리포트로 조립하는가** | **본 문서** |

db_구축_설계서.md §1.1은 자신의 범위를 "DB에 무엇을, 어떤 절차로 채워 넣는가"로 명시적으로 한정하고 있다. 그 결과 판정·조립에 관한 내용이 §6.4~6.8에 "원칙의 예외"로 산발적으로 존재해 왔다. 본 문서는 그 내용을 하나로 모으고, 지금까지 논의로만 존재하던 흐름·분기·조립 규칙을 정식 문서로 확정한다.

### 1.2 다른 문서와의 관계

| 문서 | 관계 |
|---|---|
| db_구축_설계서.md | **스키마·기준값의 원본.** 본 문서는 판정에 직접 쓰는 값을 요약 재수록하되 반드시 원본 절 번호를 병기한다 |

### 1.3 읽는 순서

구현자는 §2(리포트 구조) → §3(아키텍처) → §13(데이터 소스 매핑표) 순으로 읽으면 전체가 잡힌다. 개별 모듈을 구현할 때 §5~§9의 해당 절을 본다.

## 2. 최종 산출물 정의 — 결과 리포트 구조

본 문서 전체에서 리포트 위치를 아래 이름으로 지칭한다.

| 위치 | 이름 | 내용 |
|---|---|---|
| 상단 | 아이디어 요약 | 제목 / 앱 이름 / 특징 태그 |
| SECTION 0 | **한눈에 보기 (종합 지표)** | 규제 위험도·데이터 확보 가능성·시장 현실성을 각각 낮/중/높 신호등으로 표시 + 종합 한 줄 |
| SECTION 1 | **서비스 분류** | 타겟 상세 설명 + GATE(의료기기 여부) 판정 결과와 근거 |
| SECTION 2-1 | **규제 위험도** | 판단근거 4줄 + Before→After 표현 교정 카드 + 다음 액션 3~4개 |
| SECTION 2-2 | **데이터 확보 가능성** | 판단근거 3~4줄 + "지금 당장 모을 수 있는 것" + 단계별 로드맵 |
| SECTION 2-3 | **시장 현실성** | 판단근거 3~4줄 + 경쟁 서비스 카드 3개 + 차별화 포인트 |
| SECTION 2-4 | **수익 구조 추천** | 추천 BM 카드 2개 (지표 판정 없음, 추천만) |
| SECTION 3 | **종합 요약** | 전체 요약 + 종합 관점 다음 액션 ([지금 당장] / [출시 전 필수]) |
| 부록 | **의료기기 판정 시 처리 방안** | GATE FAIL 경로. 판정 근거 + 규제 위험도만 제공, 나머지 지표 비활성 |

## 4. 입력 명세

### 4.1 사용자 입력 (3단계 폼)

| 항목 | 형식 | 사용처 |
|---|---|---|
| 서비스 설명 | 자유 텍스트 (필수) | Stage A 키워드 스캐닝, Stage C risky_text 매칭, function_type 판별 |
| 수집할 데이터 | 복수 선택 | data_type 판별, data_sensitivity 조회, D×S 난이도 |
| 서비스 형태 | 단일 선택 (앱단독/웨어러블연동/기기연동/오프라인결합) | service_law_map, bm_mapping·competitors 조회 키, acquire_method 판별 |
| 타겟 | 선택 | bm_mapping·competitors 조회 키 |

### 4.2 카테고리 분류 모델

별도 AI 모델이 서비스 설명을 받아 **category_1(질병축 7종) + category_2(기능축 4종) 2축**을 출력한다.

- category_1: 수면 / 정신건강 / 운동 / 식단 / 만성질환 / 여성건강 / 미용
- category_2: 정보제공 / 데이터기록관리 / 매칭연결 / 개입치료

> ⚠️ **확인 필요**: 초기 설계 다이어그램에는 분류 모델이 단일 축(수면/운동/정신건강)만 출력하도록 그려져 있었다. 2축 출력 요구사항이 AI 모델 담당에게 전달됐는지 확인이 필요하다. (db_구축_설계서 §6.4 동일 항목)

### 4.3 입력 → data_type 변환 (미확정)

Step2에서 사용자가 고른 개별 항목(걸음수·심박수·생리주기 등)을 `gate_matrix.data_type`(라이프스타일/생체지표 2종)으로 변환하는 규칙이 아직 없다. `data_sensitivity` 테이블(§15.1)에 `data_type` 컬럼을 두어 항목별로 미리 매핑해두면 이 변환이 조회로 해결된다.

## 5. GATE 판정

### 5.1 Stage A — gate_keywords (1차 키워드 스캐닝)

서비스 설명 텍스트에서 위험 키워드를 스캐닝한다.

| 출력 | 값 |
|---|---|
| verdict | FAIL_CANDIDATE / CONTEXT_CHECK / FAIL_CONFIRMED |
| weight | 1~5 |
| keyword_category | DIAGNOSIS / TREATMENT / DATA_TYPE / OTHER |

이 결과는 GATE 판정뿐 아니라 §01의 `regulatory_score` 파생에도 재사용된다.

### 5.2 Stage B — gate_matrix (2차 조합 판정)

`data_type × function_type` 6칸 확정 매트릭스를 조회한다. (원본: db_구축_설계서 §3.2)

| data_type | function_type | verdict |
|---|---|---|
| 생체지표 | 단순기록 | PASS |
| 생체지표 | 비교·추이분석 | CONDITIONAL |
| 생체지표 | 수치예측·진단 | FAIL |
| 라이프스타일 | 단순기록 | PASS |
| 라이프스타일 | 비교·추이분석 | PASS |
| 라이프스타일 | 수치예측·진단 | CONDITIONAL |

**복수 조합 시**: FAIL > CONDITIONAL > PASS 우선순위로 가장 위험한 판정을 채택한다.

### 5.3 침습적 하드체크 (acquire_method 오버라이드)

`data_type=생체지표` + `acquire_method=기기연동` + Stage A에서 침습적 신호(고위해도 2번) 감지 시, **표 조회 이전에 FAIL_CONFIRMED로 하드 오버라이드**한다.

> acquire_method는 매트릭스 축을 늘리는 용도가 아니라 이 오버라이드 전용 보조 필드다. 해당 없는 일반 조합은 NULL로 둔다. (원본: db_구축_설계서 §3.2)

> ✅ **(2026-08-12 확정, 2026-08-17 판정 API 구현 완료)** 판단 기준은 **"각질층을 관통하는가"**.
> 코드 측 교차확인 키워드 13개(`app/pipeline/gate_matrix_table.py`의 `INVASIVE_KEYWORDS`) +
> `detect_invasive()`. `judgement/gate` API가 `is_invasive_hardcheck()`를 그대로 재사용해

### 5.4 GATE FAIL 분기 ⭐

**FAIL이어도 리포트를 종료하지 않는다.**

| 처리 | 내용 |
|---|---|
| 실행 | §01 규제위험도는 **끝까지 실행** |
| 스킵 | §02·§03·§04 |

| 부록 | 의료기기 판정 근거 + 회피 방향 2가지 + 규제위험도 전체 내용 |

**회피 방향 2가지**는 `gate_matrix`의 아래 두 필드에서 조회한다.

| 필드 | 내용 |

## 6. §01 규제 위험도 모듈

### 6.1 산출 흐름

```
1차: 사용자 서비스 설명 ← correction_rules.risky_text 매칭
        │ 매칭된 룰 N개
        ▼
2차: 3축 점수 확보 (각 0~3점)
     ├ regulatory_score  ◂ 매칭 룰들의 최댓값        [룰에서 조회]
     ├ advertising_score ◂ 매칭 룰들의 최댓값        [룰에서 조회]
     └ privacy_score     ◂ 사용자 Step2 수집 항목
                           → data_sensitivity 조회
                           → sensitivity_level 최댓값  [런타임 계산]
        │
3차: 축별 등급 산출 → 최고 등급 채택
     signal_config 임계값: 0~1 낮음 / 2 중간 / 3 높음
```

> ⭐ **3축의 계산 위치가 다르다 (2026-07-28 확정)**
>
> **원칙: 표현에서 결정되는 값은 룰에 저장하고, 사용자 입력에서 결정되는 값은 런타임에 계산한다.**
>
> | 축 | 결정 요인 | 어디서 오는가 |
> |---|---|---|
> | regulatory_score | risky_text(표현) | `correction_rules` 컬럼 조회 — 오프라인에서 이미 계산됨 |
> | advertising_score | risky_text(표현) | 〃 |
> | **privacy_score** | **사용자가 선택한 수집 항목** | **판정엔진이 직접 계산** — 룰에 저장돼 있지 않음 |
>
> 같은 위험표현("불면증 진단")이라도 수집 데이터가 수면(level 1)이냐 복용약물(level 3)이냐에 따라 개인정보 위험이 달라야 하므로, privacy_score는 룰에 고정 저장할 수 없다. `correction_rules.privacy_score` 컬럼은 2026-07-28 삭제됐다.
>
> **연쇄**: 3축을 모아야 하는 **최종 등급 산출도 런타임에서만 가능**하다. 오프라인 파이프라인은 2축만 산출해 룰에 저장하고 끝난다.

### 6.2 축별 산출 규칙

**regulatory_score** — 룰에서 조회 (오프라인 산출값, 원본: db_구축_설계서 §3.3)

| 점수 | 기준 (오프라인 산출 시) |
|---|---|
| 3 | gate_keywords.weight=5 또는 verdict=FAIL_CONFIRMED 매칭 |
| 2 | weight 3~4 매칭 |
| 1 | weight 1~2 매칭 |
| 0 | 매칭 없음 |

> 판정엔진은 매칭된 룰 N개의 `regulatory_score` 중 **최댓값**을 취한다.

**advertising_score** — 룰에서 조회 (오프라인 산출값, 원본: db_구축_설계서 §3.3)

| 점수 | 별표7 항목 |
|---|---|
| 3 | 1·2·4·8·9·15·17·18호 (허위·과대광고) |
| 2 | 3·5·6·7·10·11·14호 |
| 1 | 12·13·16호 |
| 0 | 해당 없음 |

> 판정엔진은 매칭된 룰 N개의 `advertising_score` 중 **최댓값**을 취한다.

**privacy_score** — 🔵 **판정엔진이 직접 계산** (원본: db_구축_설계서 §3.3.2)

```
입력: 사용자가 Step2에서 선택한 수집 데이터 항목 (복수)
   ↓ data_sensitivity.item_label 로 조회
sensitivity_level 획득 → 최댓값 채택
```

| sensitivity_level | privacy_score |
|---|---|
| 3 | 3 |
| 2 | 2 |
| 1 | 1 |
| 미포함 | 0 |

> ⚠️ **`item_label` 표기가 Step2 UI 옵션 문자열과 글자 단위로 일치해야 한다.** 사용자 선택값으로 직접 조회하므로 "심박수" vs "심박 수" 같은 차이도 조회 실패를 일으키고, 실패 시 해당 항목의 민감도가 **조용히 누락**된다. 조회 실패 시 로그를 남겨 감지할 수 있게 구현할 것.

> ✅ **동의 언급 여부는 산출에서 제외됨** — 아이디어 입력 폼에 동의 항목이 없어 자유 텍스트 추출에 의존해야 하고, 선언만으로 점수가 낮아져 변별력이 없으며, 동의 취득이 실제 규제 부담을 줄이지도 않기 때문. 동의 요건은 `action_templates`의 `sensitivity_level=3` 트리거 액션으로 안내한다.

### 6.3 최종 등급 — 합산이 아닌 최고값 (🔵 런타임 전용)

3축 점수를 **합산하지 않고**, 축별 등급을 매긴 뒤 **최고 등급을 최종 위험등급으로 채택**한다.

> 🔵 **이 계산은 판정엔진에서만 수행된다.** privacy_score가 사용자 입력에서 결정되므로 오프라인 파이프라인은 3축을 모을 수 없어 등급을 확정할 수 없다. (2026-07-28 확정, db_구축_설계서 §3.3.2)

> 합산을 쓰지 않는 이유: 광고 축만 3점인 경우 합산 3점 → "중간"으로 분류되는데, 별표7 3점 항목은 그 자체로 즉시 시정 대상이라 과소평가 위험이 크다.

합산점수(0~9)는 판정에 쓰지 않고 리포트 SECTION 2-1 판단근거에 **참고 수치로만** 노출한다.

`LegalBasis`는 `app/schemas/common.py`에 공용 정의 — 세 API가 공유. `quote`는 RAG `rag/chunks/lookup` 연동 전까지 항상 `null`(룰 테이블엔 조문 원문이 없음, evidence_chunks 조회로만 채워짐).

`match_source`(2026-08-25, D-15)는 이 후보가 `correction_rules` 규칙 기반 매칭인지 이슈 #58의 LLM① 폴백 추정인지 구분한다. `regulatory_score`/`advertising_score`는 여전히 규칙 기반만 반영하므로(§10.1 원칙 유지), `regulatory_grade`가 "낮음"인데 LLM이 찾은 후보가 같이 뜨는 조합이 나올 수 있다 — 프론트는 `match_source: "llm"`인 후보에 "AI 추정" 캡션을 붙이는 걸 권장.

**⚠️ §6.2 대비 변경 — regulatory_score 매칭 보강**

§6.2 원안은 "매칭된 룰(`correction_rules`) N개의 최댓값"만 취했는데, 실제로 테스트해보니 `correction_rules.risky_text`(104개, 이미 완성된 짧은 정형 문구, 예: `"혈당 검사"`)가 자연스러운 서비스 설명 문장에 **문자 그대로** 안 들어있으면 전혀 매칭이 안 됐다(예시: `"혈당 수치값을 표시하고 위험 수치일 때 경고 알람을 제공한다."` → 매칭 0건).

→ `gate_keywords`(68개, "혈당"처럼 단어 단위) 직접 매칭을 병행해 **둘 중 높은 점수를 채택**하도록 보강. `extract_c.py._keyword_score`(weight→점수 변환 공식)를 그대로 재사용해 오프라인 산출 기준과 일치시켰다.

`correction-candidates`(교정 후보, Before→After 카드 원천)도 같은 문제가 있어, `correction_rules.derived_from_keyword_id` FK(원래 "이 문구가 어느 gate_keywords에서 파생됐는지" 추적용)를 **역방향으로 활용** — 텍스트에서 매칭된 `gate_keywords`가 있으면 그 keyword_id로 파생된 `correction_rules`도 후보에 포함시킨다. 활성 104건 중 95건이 이 FK를 갖고 있어 커버리지가 크다.

효과(같은 예문 기준): `matched_rules`/`candidates` 0건 → 3건, 그중 하나가 정확한 근거 조문(`kr-mfds-wellness-0091-03-20260212 IV.3`)으로 확인됨.

> ⚠️ **알려진 한계**: `advertising_score`는 여전히 `correction_rules` 매칭에만 의존한다 — 3축 중 유일하게 LLM 판단 영역으로 설계된 축이라(§6.2) 완전한 규칙 기반 대안이 없다. 별표7 신호어 목록(`extract_c.py` 프롬프트에 하드코딩)을 상수로 빼서 보강하는 방안을 검토했으나 아직 미착수.
>
> ⚠️ **`item_label` 표기 불일치가 실제로 재현됨**: mock 테스트 중 `"복용약물"`(공백 없음)이 실제 DB의 `"복용 약물"`(공백 있음)과 안 맞아 조용히 `privacy_score=0` 처리되는 걸 확인했다 — §6.2의 경고가 실전에서 그대로 발생. 2번·프론트 담당과 표기 협의 필요(미결정_항목_정리.md 참조).

```
④ (조건부) 🔗 타 섹션 연결 안내
```

> ⚠️ **리포트 명세 수정 필요**: 결과 리포트 명세는 🔴 사유를 "임상·진료 데이터 등 직접 수집 불가"로 서술하나, 임상·진료가 1차 구축에서 제외되면서 이 예시는 성립하지 않는다. **"생체지표를 기기연동·기관연동으로 확보해야 하는 경우"**로 재정의할 것.

### 7.3 데이터 종류 3분류

| 종류 | 조회 테이블 | 예시 |
|---|---|---|
| 자가 입력 데이터 | ★ standard_scales | 취침/기상 시간, 기분, PHQ-9 |
| 공개 통계 데이터 | ★ public_data_catalog | 국민건강영양조사, KDCA 통계 |
| 공개 API 데이터 | ★ api_catalog | Apple HealthKit, Health Connect |

### 7.4 단계별 로드맵

`★ mvp_strategy_templates`를 난이도 × STAGE(1 MVP / 2 검증 / 3 확장)로 조회한다.

> **작성 원칙**: STAGE 1은 항상 즉시 실행 가능한 수준으로 제시하고, "불가능" 대신 "단계적으로" 방향으로 출력한다. 데이터 확보가 어렵다고 판정돼도 사용자를 빈손으로 돌려보내지 않는 것이 이 섹션의 설계 의도다.

## 8. §03 시장 현실성 모듈

### 8.1 경쟁 포화도 — 개수 기반

```
n = 조회 범위 내 경쟁사 COUNT

n = 0~2                        → Opportunity  (시장현실성 높음)
n = 3~4                        → Challenging  (시장현실성 중간)
n >= 5                         → Saturated 후보
n >= 5 AND tier='플랫폼' 존재   → Saturated    (시장현실성 낮음, 확정)
```

> ⚠️ **역관계 주의**: 포화도가 **낮을수록** 시장현실성 지표는 **높다**. 구현·문구 작성 시 가장 혼동하기 쉬운 지점이다.

> 원본: db_구축_설계서 §3.5. 가중합 공식(`Σ(체급점수 × 유사도가중치)`)은 미확정 수치를 7개나 요구하고 "유사도" 계산 정의도 없어 90건 시드로는 캘리브레이션이 불가능해 폐기했다. `competitor_tier_score`(5/3/1)는 가중치가 아닌 **플랫폼 존재 판별 플래그**로만 쓰인다.

### 8.2 조회 범위 — 4단계 완화 전략 (§04와 공유)

```
1) exact_match          : category_1 + category_2 + target + service_type 전부 일치
2) relaxed_service_type : service_type 조건 해제
3) relaxed_category_only: category_1 + category_2 만 일치
4) insufficient_data    : 위 3단계 모두 n=0
```

4개 키를 모두 맞춰 세면 시드 90건이 잘게 쪼개져 대부분 n≤2로 나와 무조건 Opportunity가 된다. 완화 전략을 적용하면 시장현실성(§03)과 BM 추천(§04)이 같은 조회 전략을 공유해 구현·설명이 단순해진다. **리포트에는 어느 단계에서 매칭됐는지(match_level)를 함께 표기**해 근거 신뢰도를 드러낸다.

### 8.3 국내 수요 판정

**앱스토어 순위 기준** (원본: db_구축_설계서 §3.9)

| 해당 category_1 앱 중 최고 순위 | 판정 |
|---|---|
| 100위 이내 | 상위권 |
| 101~300위 | 중위권 |
| 300위 밖 또는 없음 | 낮음 |

건강·피트니스 카테고리 **무료 순위** 기준.

**검색 트렌드 분석** (원본: db_구축_설계서 §6.8)

```
[1단계] 성장 업종 10개 + 정체/하락 업종 10개 선정
[2단계] 각 업종 12개월 검색지수로 최소제곱법 기울기(a) 산출
[3단계] 두 그룹 기울기 분포의 교차점 = 임계값
[4단계] 성장 그룹 1사분위수로 최종 검증
```

| 조건 | 판정 |
|---|---|
| 기울기 > 임계값 | 급성장 |
| 0 < 기울기 < 임계값 | 완만 |
| 기울기 < 0 | 하락 |

**보완 4가지 (필수)**

| # | 항목 | 내용 |
|---|---|---|
| ① | 앵커 키워드 | 데이터랩 정규화는 한 호출 안에서만 유효. 배치마다 공통 앵커를 넣어 스케일 보정 |
| ② | 계절성 보정 | 12개월 단일 사이클로는 계절성과 성장 구분 불가. 24개월 수집 + 전년 동월 대비 병행 |
| ③ | R² ≥ 0.3 | 미달 시 "변동성 큼 — 판별 불가"로 처리, 급성장/하락 판정 부여 안 함 |
| ④ | 저검색량 제외 | 12개월 중 0이 3개월 이상이면 "데이터 부족" 처리 |

> **트렌드 계산은 런타임 모듈이며 테이블이 아니다.** 단 임계값은 사전 산출한 고정값이므로 별도 설정 테이블 또는 코드 상수로 저장한다. 외부 API 지연·호출한도 대응을 위해 24시간 캐시를 권장한다.

### 8.4 시장현실성 신호등 매핑

| 포화도 | 시장현실성 지표 |
|---|---|
| Opportunity | 높음 |
| Challenging | 중간 |
| Saturated (후보 포함) | 낮음 |

### 8.5 경쟁 서비스 카드

- 노출 개수: **3개** (`LIMIT 3`)
- 카드 구성: 서비스명 · 특징 1줄 · **한계 1줄** · 배지
- 한계 1줄은 `competitors.limitation` ☆ (신설 필드)
- 배지 기준: 차별화 여지 있으면 "진입 가능" / 대형 서비스가 동일 기능 제공 시 "차별화 필요"

## 9. §04 수익 구조 모듈

### 9.1 bm_mapping VIEW 조회

`bm_mapping`은 저장 테이블이 아니라 `competitors`를 실시간 집계하는 **VIEW**다.

```sql
SELECT bm_pattern, frequency_score, frequency_score_global,
       precedent_level, contributing_competitor_ids
FROM bm_mapping
WHERE category_1 = :c1 AND category_2 = :c2
  AND target = :target AND service_type = :service_type
ORDER BY frequency_score DESC
LIMIT 2;
```

§8.2의 4단계 완화 전략을 동일하게 적용한다.

### 9.2 출력

- 추천 BM **2개** (좌/우 카드)
- 각 카드: BM 유형 / 이름 / 4줄 요약(가격대·전환율·강점 등)
- match_level 표기 (근거 신뢰도)
- **지표 판정 없음** — 높/중/낮 등급을 매기지 않고 추천만 제공

> `insufficient_data`면 bm_pattern 추천 없이 "검증 필요"로 표시하고 수치·근거를 임의 생성하지 않는다.

### 9.3 카드 4줄 요약의 데이터 부족

| 항목 | 상태 |
|---|---|
| 가격대 | `competitors.price` ☆ 신설 필요 (현재 note에 자연어로만 존재) |
| 전환율 | **수집 가능성 미확인** — 대부분 비공개 수치 |
| 강점 | bm_pattern + competitors 정보로 LLM ③ 생성 |

## 10. RAG 결합 방식

### 10.1 원칙 — 판정에는 영향 없음

verdict(PASS/FAIL), 3축 점수, 신호등 등급, 포화도는 **전부 룰 테이블 조회만으로 결정**된다. RAG 검색 결과가 무엇이든 이 값들은 바뀌지 않는다. RAG를 꺼도 등급은 동일하게 나온다.

### 10.2 두 가지 호출 경로

**① ID 기반 조회 — 조문 원문 렌더링 (결정론적)**

룰 테이블이 이미 `legal_basis_doc` / `legal_basis_article`로 어느 조문이 근거인지 저장하고 있다. RAG는 그 ID로 `evidence_chunks`에서 **원문 텍스트를 꺼내오는 역할**만 한다. 검색도 판단도 없어 매번 동일한 결과가 나온다.

```
correction_rules: legal_basis_article = "의료법 제27조"
        ↓
evidence_chunks 조회 → 조문 원문
        ↓
리포트에 근거로 표시
```

**② 검색 기반 조회 — 유사 사례 탐색 (비결정론적)**

벡터 검색으로 규제 위반 사례·스타트업 IR·BM 논문 등을 찾는다. 결과가 매번 달라질 수 있고, **LLM 입력으로 들어가 서술을 바꾼다.**

### 10.3 검색 결과 개수

| 용도 | 개수 |
|---|---|
| 조문 근거 (ID 기반) | 전량 |
| 유사 사례 (벡터 검색) | **top-3** |

### 10.4 리포트 내 출현 위치

| 위치 | 역할 |
|---|---|
| SECTION 1 서비스 분류 | GATE 판정 근거 조문 (①) |
| SECTION 2-1 규제 위험도 | 판단근거 법령 인용, 액션 참고자료 inline (①) |
| SECTION 2-2 단계별 로드맵 | 카테고리별 사례 참고 (②) |
| SECTION 2-3 시장 현실성 | 스타트업 IR 사례 보조 근거 (②) |
| 부록 | 의료기기 판정 근거 (①) |

### 10.5 판단가이드 적재 방침 (2026-07-26 확정 — 안 B)

의료기기 판단가이드(지침서-0091-03, 모바일 의료용 앱 안전관리 지침, LLM 디지털의료기기 가이드라인)는 **룰베이스 추출과 RAG 근거 제공 양쪽에 사용**한다. `evidence_documents.usage_scope = BOTH`.

이 결정이 없으면 아래 두 블록을 채울 수 없다.

| 리포트 위치 | 필요한 것 |
|---|---|
| SECTION 1 서비스 분류 — "GATE 판정 결과 및 근거" | gate_matrix가 지정한 지침서 조문(예: `0091-03 Ⅳ.3`)의 원문 |
| 부록 — "의료기기 판정 근거 제공" | 동일 |

판단가이드가 evidence_chunks에 없으면 "의료기기로 판정되었습니다"만 표시되고 **판정 이유를 보여주지 못한다.** (원본: db_구축_설계서 §1.4)

### 10.6 조회 인터페이스 — load_shared_chunks (RAG 담당 제안, 합의 대기)

RAG 담당이 제안한 `load_shared_chunks` 노드 인터페이스는 §10.2의 두 경로와 정확히 대응한다.

**ID 기반 조회 (§10.2 ①에 대응)**

```json
// 입력
{ "document_id": "kr-pipa-active-20251002",
  "section_id": "제23조",
  "chunk_type": "ARTICLE" }

// 출력
{ "chunk_id": "kr-pipa-active-20251002__0023",
  "document_id": "kr-pipa-active-20251002",
  "section_id": "제23조",
  "section_title": "제23조(민감정보의 처리 제한)",
  "chunk_text": "...",
  "source_url": "...", "page_start": 12, "page_end": 13,
  "effective_date": "2025-10-02", "status": "active" }
```

**검색 기반 조회 (§10.2 ②에 대응)**

```json
{ "query": "민감정보 건강정보 처리 제한",
  "tag_privacy": true,
  "status": "active" }
```

> ✅ **section_id 표기 규칙 확정 (2026-07-28)**: 룰베이스 `legal_basis_article`과 RAG `section_id`는 **동일 규칙**을 사용한다. 원문 목차 표기를 기본으로 하되 로마숫자 ASCII 통일(`Ⅲ`→`III`), 마침표 구분자, 공백 제거, `별표7.제8호` 형식을 적용한다. 원문 표기는 `section_title`에 보존. **전체 규칙은 db_구축_설계서 §1.5.1 참조.**

> ✅ **별표7 항목 번호 단위 분할 확정 (2026-07-28)**: `advertising_score`가 별표7 18개 항목 번호에 매여 있으므로 `별표7.제8호` 단위로 chunk를 분할한다. 이로써 판정 근거를 항목 단위로 인용할 수 있어 SECTION 2-1의 "참고 법령 inline 표시"를 충족한다.

### 10.7 "항상 호출"의 의미와 주의점

GATE FAIL이어도 호출한다. 부록에서 "왜 의료기기로 판정됐는지" 근거를 보여줘야 하기 때문이다.

> ⚠️ **원칙이 LLM 단계에서 새는 지점**: ②번 검색 결과가 LLM 프롬프트에 들어가면 LLM이 "유사 사례를 보니 위험해 보입니다" 같은 서술을 만들 수 있다. 등급은 안 바뀌었는데 **읽는 사람이 체감하는 판정은 흔들린다.** LLM 프롬프트에 "RAG 결과는 근거 예시로만 인용하고 위험도에 대한 새로운 판단을 하지 말 것"을 명시해야 한다.

> ⚠️ **재현성**: ②는 벡터 검색이라 같은 입력에 다른 chunk가 나올 수 있어 리포트 문장이 매번 미묘하게 달라진다. 허용 범위를 팀에서 정할 것.

## 11. 종합 신호등 산출

SECTION 0 최상단의 종합 판정 규칙.

```
빨강 = 규제위험도 '높음' OR 데이터확보 '어려움'

초록 = 규제위험도 '낮음'
       AND 데이터확보 IN ('쉬움','보통')
       AND 시장현실성 '높음'
       AND BM추천 존재 (match_level != 'insufficient_data')

노랑 = 빨강·초록 어디에도 해당하지 않을 때
```

### 11.1 "수익 높음" 대신 "BM추천 존재"를 쓰는 이유

결정3 원안은 `(시장 OR 수익 중 하나 높음)`이었으나, **시장현실성과 수익 선례는 동일한 데이터(경쟁사 수)에서 파생되는 상관 지표**다.

| 경쟁사 수 | 시장현실성 | 수익 선례 |
|---|---|---|
| 적음 | 높음 | 적음 |
| 많음 | 낮음 | 많음 |

OR 조건이 거의 항상 참이 되어 조건이 무력화된다. 또 결과 리포트 명세는 수익구조를 "BM 추천만, 지표 판단 없음"으로 규정해 높/중/낮 등급 자체가 없다.

따라서 수익 축은 등급이 아니라 **"근거를 댈 수 있는가"라는 안전장치**로 재정의한다. 경쟁사 데이터가 부족해 BM 추천조차 못 내는 경우 초록을 부여하지 않는다.

### 11.2 GATE FAIL 시

종합 신호등은 규제위험도만으로 판정하고, 데이터확보·시장현실성은 비활성 처리한다.

## 12. LLM 호출 구조

> ✅ **"LLM 호출 3회 고정" 제약은 폐기됨.** 호출 횟수는 비용·지연의 실제 결정 변수가 아니다(비용은 토큰량, 지연은 병렬화 여부가 좌우).

| 단계 | 호출 | 실행 | 산출물 |
|---|---|---|---|
| 1단계 | ① 표현 대체어 생성 | 병렬 | SECTION 2-1 Before→After 카드 |
| | ② 차별화 포인트 제안 | 병렬 | SECTION 2-3 |
| | ③ BM 카드 4줄 요약 | 병렬 | SECTION 2-4 |
| 2단계 | ④ 종합 요약 | 순차 | SECTION 3 |
| | ⑤ 한 줄 총평 | 순차 | SECTION 0 |

총 지연 = `max(①②③) + max(④⑤)`

### 관리 원칙 3가지

1. **LLM 불가침 값 고정** — 판정 결과·축별 점수·신호등 등급은 LLM이 생성하거나 변경할 수 없다. 코드가 산출한 값을 프롬프트에 주입만 하고 **출력 스키마에서 해당 필드를 제외**해 구조적으로 차단한다. (Stage B의 "LLM은 data_type/function_type만 판단, verdict는 코드가 표 조회로 채움" 패턴과 동일)
2. **호출 간 모순 방지** — 2단계 호출(④⑤)에는 1단계 결과를 전부 주입한다. 미주입 시 "SECTION 2-3은 경쟁 치열이라 썼는데 SECTION 0 총평은 블루오션" 같은 상호 모순이 발생한다.
3. **병렬/순차 구분** — 위 표대로 1단계 3개는 병렬, 2단계 2개는 후행.

> ⚠️ **최대 리스크 항목** — 조사가 아니라 창작이라 진행이 막히기 쉽다. 여기가 막히면 앞의 테이블을 다 만들어도 SECTION 2-2가 "판정은 나오는데 조언이 없는 섹션"으로 남는다.
