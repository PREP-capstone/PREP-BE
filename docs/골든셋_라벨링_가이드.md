# 골든셋 라벨링 가이드

> 버전: v0.1 (초안) | 2026-10-01
> 목적: PREP 판정의 **타당성**(결과가 맞는가)을 재기 위한 정답지(골든셋)를 만드는 규칙.
> 교수님 피드백("어떤 기준으로 테스트했는가", "결과가 의미 있게 나왔다는 근거") 대응용.
> 함께 보는 것: `data/eval/golden_set_template.csv`(입력 형식), `scripts/eval_reliability.py`(측정 스크립트)

---

## 0. 핵심 원칙 3가지

1. **정답은 팀 의견이 아니라 외부 근거 문서에서 온다.** 출처(문서·조문)가 없는 행은 넣지 않는다.
   "우리가 정한 답에 시스템을 맞췄다"는 비판을 피하려면 정답의 근거가 시스템 밖에 있어야 한다.
2. **개발에 쓴 예시는 평가에 쓰지 않는다(dev/test 분리).** 규칙·프롬프트를 만들 때 이미 본 예시로
   평가하면 답을 보고 시험 보는 셈이다. 메인 결과는 `test` 행으로만 보고한다.
3. **평가자는 PREP의 판정표가 아니라 원문을 보고 라벨을 단다.** 6칸 매트릭스를 보고 라벨을 달면
   정답이 시스템을 그대로 베낀 값이 되어 측정 의미가 없다.

## 1. 작업 순서

| 단계 | 하는 일 | 결과 |
|---|---|---|
| 1 | `golden_set_template.csv`를 복사해 `data/eval/golden_set.csv`로 만든다 | 작업 파일 |
| 2 | 행 작성자가 입력 칸(서비스 설명·데이터 항목·기능 등)과 출처 칸을 채운다 | 미라벨 행 |
| 3 | 평가자 2~3명이 **서로 보지 않고** `rater_1_gate`~`rater_3_gate`를 채운다 | 독립 라벨 |
| 4 | `python scripts/eval_reliability.py kappa --golden data/eval/golden_set.csv` | 평가자 일치도(κ) |
| 5 | 불일치 행만 모여 원문을 대조하고 `expected_gate_verdict`와 `label_rationale`을 확정한다 | 정답 라벨 |
| 6 | `python scripts/eval_reliability.py run --golden data/eval/golden_set.csv --split test` | 타당성·재현성 결과 |

평가자 일치도는 **라벨 자체의 신뢰도**다. κ가 낮으면(아래 §6) 시스템을 평가하기 전에 라벨 기준부터 다시 맞춘다.

## 2. 정답 출처 — 우선순위

| 순위 | 출처 | 쓰임 | 예 |
|---|---|---|---|
| 1 | 식약처 지침·가이드라인의 명시적 예시 | GATE | 웰니스 판단기준(0091-03) IV.1·IV.3, 모바일 의료용 앱 안전관리 지침 |
| 2 | 실제 허가·인증 사례 | GATE (FAIL 정답) | 의료기기 정보포털에서 허가된 디지털치료기기·소프트웨어 의료기기 |
| 3 | 시판 중인 웰니스 앱 | GATE (PASS 정답) | 앱마켓의 건강·피트니스 앱 중 의료기기 허가 없이 판매 중인 것 |
| 4 | 정부 사례집 | 규제위험도 | 비의료 건강관리서비스 가이드라인 및 사례집(2차)의 허용/불허 사례 |
| 5 | 적발 사례 | 광고 축 | 식약처 허위·과대광고 적발 보도자료 |

- 2·3번(실제 제품)은 서비스 설명을 **자기 말로 요약**해서 적는다. 앱 소개 문구를 그대로 복사하지 않는다
  (지식재산권 — 팀 규칙 2번).
- 출처 URL은 직접 열어 확인한 페이지만 적는다.

## 3. dev / test 구분

| split | 기준 |
|---|---|
| `dev` | 규칙·프롬프트·테스트 코드·설계 문서에 이미 등장한 예시. 판단이 애매하면 dev |
| `test` | 개발 과정에서 한 번도 쓰지 않은 예시. 메인 결과는 이 행으로만 계산 |
| `example` | 형식 참고용(템플릿 예시). 결과 계산에서 빼려면 `--split test`로 실행 |

- 누수 확인: 서비스 설명의 핵심 구절로 저장소를 검색한다. 예: `git grep "위험 수치일 때"`
  → `app/pipeline/nodes/extract_b.py` 프롬프트에 있으므로 dev.
- `docs/리포트_구현_격차_정리.md`의 2026-08-23 실측 문장 10개(복약지도·트리아지·정신건강 상담 등)는
  LLM① 폴백을 설계할 때 쓴 문장이라 dev다. 위험 표현 탐지(paraphrase) dev 행의 출발점으로 쓰면 좋다.
- **test 결과를 보고 규칙을 고쳤다면** 그 행은 dev로 옮기고 새 test 행을 추가한다. 그렇지 않으면
  test 점수가 점점 "답을 본 시험"이 된다.

## 5. 구성 목표

- 판정 클래스별 15~20건, 총 60건 안팎 (`PASS` / `CONDITIONAL` / `FAIL`이 한쪽으로 쏠리지 않게).
- 견고성 태그별 최소 3건. 전부 **팀이 실제로 겪은 버그 유형**이라 "왜 이 케이스를 넣었나"에 바로 답할 수 있다.

| 태그 | 무엇을 보나 | 실제 사례 |
|---|---|---|
| `negation` | 부정 표현을 위험으로 오인하지 않는가 | "비침습적", "비이식형"이 침습으로 뒤집힌 버그 |
| `paraphrase` | 키워드 없이 돌려 말한 위험 문장을 잡는가 | 규칙만으로 위험 문장 8개 중 4개를 놓친 실측(2026-08-23) |
| `dictionary_gap` | 사전에 없던 항목을 놓치지 않는가 | "심박수", "유전자"가 생체지표로 인식 안 된 버그 |
| `input_conflict` | 설명문과 선택값이 어긋날 때 | 설명엔 "진단", 기능 체크는 "기록"만 |
| `invasive` | 침습적 하드체크 | CGM, 마이크로니들 vs 부착형 패치 |
| `genetic` | 유전자검사(생명윤리법) 안내 | DTC 유전자검사 키트 |
| `advertising` | 광고 표현 축 | "100% 완치", "부작용 없음" 같은 별표7 표현 |

## 6. 판정 라벨 정의와 일치도 해석

| 라벨 | 뜻 |
|---|---|
| `PASS` | 의료기기 해당 가능성이 낮다(일상적 건강관리·저위해도) |
| `CONDITIONAL` | 조건에 따라 갈린다 — 추가 검토가 필요하다 |
| `FAIL` | 의료기기 해당 가능성이 높다(질병 진단·예측 목적, 고위해도) |

평가자 일치도 κ 해석(Landis & Koch, 1977): 0.41~0.60 보통 / **0.61~0.80 상당한 일치** /
0.81 이상 거의 완전한 일치. 목표는 0.61 이상이다. 그 아래면 §6 라벨 정의를 예시와 함께 더 구체화한 뒤
다시 라벨링한다.

## 7. 합격 기준은 테스트 전에 확정한다

측정 지표와 합격 기준은 `run`을 돌리기 **전에** 팀 회의로 확정하고, 바꾸면 변경 이력을 남긴다.
결과를 보고 기준을 바꾸면 "어떤 기준으로 테스트했는가"에 답할 수 없다. 현재 초안 기준은 팀 공유 문서
"PREP 신뢰성·타당성 검증 계획"의 재현성·타당성 절을 따른다.
