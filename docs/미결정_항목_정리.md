### ~~E-1. correction_rules 3축 점수의 계산 위치~~ ✅ **2026-07-28 해결**

**결정**: 축별로 분리합니다.

| 축 | 결정 요인 | 계산 위치 |
|---|---|---|
| regulatory_score | risky_text(표현) | 오프라인 — 룰에 저장 |
| advertising_score | risky_text(표현) | 오프라인 — 룰에 저장 |

**원칙**: *표현에서 결정되는 값은 룰에 저장하고, 사용자 입력에서 결정되는 값은 런타임에 계산한다.*

**연쇄 결정**: 3축을 모아야 하는 최종 위험등급 산출(축별 등급 → 최고값)도 런타임으로 이관.

**담당 영향**: 담당 E의 Stage C 작업이 "privacy_score 교체"에서 "제거"로 축소되고 `data_sensitivity` 의존이 사라짐(A-1 블로커 해소). FastAPI팀에 privacy_score 계산 + 최종 등급 산출이 추가됨.

상세 근거는 db_구축_설계서 §3.3.2, 판정엔진_개발설계서 §6.1~6.3 참조.

### E-2. 카테고리 분류 모델의 출력 축

초기 설계 다이어그램에는 분류 모델이 **단일 축**(수면/운동/정신건강)만 출력하도록 그려져 있으나, 현재 DB는 `category_1`(질병축 7종) + `category_2`(기능축 4종) **2축**을 요구합니다.

**영향**: 2축 출력이 안 되면 `bm_mapping`·`competitors` 조회 키가 비어 §03·§04 모듈이 동작하지 않습니다. AI 모델 담당에게 요구사항이 전달됐는지 확인 필요.

### E-3. Step2 입력 → data_type 변환 규칙

사용자가 Step2에서 고른 개별 항목(걸음수·심박수·생리주기)을 `gate_matrix.data_type`(라이프스타일/생체지표 2종)으로 변환하는 규칙이 없습니다.

**해결 방향**: `data_sensitivity`에 `data_type` 컬럼을 두어 항목별로 미리 매핑하면 조회로 해결됩니다. → **A-5(data_sensitivity 스키마 확정) 시 함께 처리**

### E-4. 리포트 저장 정책

PREP §10.4는 "사용자 입력·분석 결과 미저장"인데, 리포트 재조회와 창업제안서·지원사업 매칭 단계로의 데이터 전달 방식이 미정입니다.
