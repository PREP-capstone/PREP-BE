## A. 이미 DB에 있는데 API가 활용을 안 하는 것 (우선순위 최상)

새 테이블을 만들 필요가 없다 — 조회 로직 + 트리거 매칭 코드만 있으면 된다.

### A-1. `action_templates` — ✅ scope=SECTION 완료(2026-08-23), OVERALL 조회만 남음

```
template_id / scope(SECTION|OVERALL) / trigger_type / trigger_value /
action_text / ref_doc / tag(지금당장|출시전필수) / priority
```

- **쓰이는 곳**: SECTION 2-1 "다음 액션 3~4개"(scope=SECTION), SECTION 3 "지금 당장/출시 전 필수"(scope=OVERALL), 부록 — 리포트에서 세 번 쓰이는 유일한 테이블(`판정엔진_개발설계서.md` §15.3)
- **트리거 종류**: `gate_verdict` / `risk_level` / `data_level` / `market_level` / `sensitivity_level` — 전부 `evaluate` 응답에 이미 있는 값들(`gate.verdict`, `regulatory_risk.*_grade`, `data_feasibility.risk_level`, `market_feasibility.market_realism_grade`, 항목별 `sensitivity_level`)이라 **매칭 키는 이미 다 갖고 있음**
- **콘텐츠 현황(2026-08-23 최종)**:
  | scope | 행 수 |
  |---|---|
  | OVERALL | 17 (미조회 — SECTION 3 "지금당장/출시전필수"용, 조회 함수만 남음) |
  | SECTION | **5** — ✅ 완료. gate_verdict(FAIL) 1, risk_level(낮음/중간/높음) 3, sensitivity_level(3) 1 — §15.3의 "필수 시드 액션"(별도 동의 안내) 포함 |
- **완료된 것**: `evaluate.py`의 `_find_next_actions()` — `gate.verdict`+`regulatory_risk.regulatory_grade`+`.privacy_score`로 scope=SECTION 조회, priority 상위 4개만 노출(§15.3 조합 폭발 방지). `EvaluateResult.next_actions` 필드로 노출됨
- **남은 것**: OVERALL(scope=SECTION 3용) 조회 함수만 남음 — 콘텐츠는 이미 있음

### A-2. `mvp_strategy_templates` — **9행 전부 완비**, 조회 API 없음

```
template_id / category_1(nullable) / difficulty_level(쉬움|보통|어려움) /
stage(1 MVP|2 검증|3 확장) / title / description
```

- **쓰이는 곳**: SECTION 2-2(데이터 확보 가능성) "단계별 로드맵 STAGE 1/2/3"(신호등 무관 항상 출력) + "🔴 MVP 전략 박스"
- **실측 콘텐츠 현황**: 난이도(쉬움/보통/어려움) × 스테이지(1/2/3) = 9칸 **전부 채워짐**(category_1=NULL, 설계서 §15.7이 말한 "1차 완료" 기준 그대로 충족) — **콘텐츠는 완성, 조회 API만 없음**
- **막힌 지점**: `data_feasibility.risk_level`(LOW/MEDIUM/HIGH) → `difficulty_level`(쉬움/보통/어려움) 매핑 후 `stage` 3개 조회하는 함수만 추가하면 즉시 사용 가능
- **소유**: SECTION 2-2(`feasibility/data`) 담당은 **2번으로 확정**(F-1 해결)

### A-3. `trend_signal_config` — 7행 시드됨, 조회 API 없음

- **쓰이는 곳**: SECTION 2-3(시장 현실성) 판단근거① "국내 수요" — 검색 트렌드 임계값
- **막힌 지점**: `feasibility.py` 상단 주석에 이미 적혀있음 — "검색 트렌드 임계값은 산출됐으나 성장군/정체군 그룹 가정이 예상과 어긋나 팀 재검토 대기"(`app/api/feasibility.py:276-282`). 즉 코드 문제가 아니라 **산출 로직 자체의 가정이 재검토 대상** — A-1/A-2와 달리 조회 코드부터 짜면 되는 게 아니라 먼저 로직을 다시 봐야 함
- 3번(시장성) 소관

## C. 테이블/API 유무와 무관하게 아예 없는 것 — LLM 생성 콘텐츠

`판정엔진_개발설계서.md` §12(LLM 호출 구조)에 5개 호출이 이미 설계돼 있지만, **코드베이스 전체를 뒤져도 리포트용 LLM 호출은 단 한 줄도 없다**(`app/pipeline/`의 LLM은 오프라인 룰 추출용이라 완전히 다른 용도).

| # | 산출물 | 위치 | 실행 방식(설계상) |
|---|---|---|---|
| ① | 표현 대체어 생성 | SECTION 2-1 Before→After 카드 | **폴백만**(0건일 때) — 아래 "① 재검토" 참고, 실측 완료 |
| ② | 차별화 포인트 제안 | SECTION 2-3 | 병렬 |
| ③ | BM 카드 4줄 요약 | SECTION 2-4 | 병렬 (§9.3 "카드 4줄 요약의 데이터 부족" 참고 — 데이터 자체도 부족하다고 명시됨) |
| ④ | 종합 요약 | SECTION 3 | 순차, ①②③ 결과 전부 주입 필요 |
| ⑤ | 한 줄 총평 | SECTION 0 | 순차, ①②③ 결과 전부 주입 필요 |

- SECTION 0 "종합 신호등"(규제·데이터·시장 3개 등급 + BM추천 존재 여부를 합친 색)도 계산 로직이 코드에 없음 — `evaluate` 응답을 프론트가 조합하거나, 이 조합 로직을 백엔드에 새로 만들어야 함(§11)
- 설계서 §12 "관리 원칙"에 이미 "④⑤ 호출 시 ①②③ 결과를 전부 주입해야 섹션 간 모순이 안 생긴다"는 순서 제약이 적혀있어, 구현 시 이 순서를 그대로 지켜야 함

### ① "표현 대체어 생성" — 재검토 결과: **필요함. 폴백 형태로 축소 구현 권장**

원래 LLM①이 필요했던 이유: `correction_rules.risky_text`가 짧고 정형화된 문구("혈당 검사")라 자연스러운 서비스 설명 문장엔 그대로 안 들어있어 매칭이 거의 안 됐음(예: "혈당 수치값을 표시하고 위험 수치일 때 경고 알람을 제공한다." → 매칭 0건).

`correction-candidates` 구현(2026-08-17, `판정엔진_개발설계서.md:445-453`)이 이 문제를 어느 정도 고쳤음 — `gate_keywords`(68개, 단어 단위) 직접 매칭을 병행하고, `correction_rules.derived_from_keyword_id` FK를 역방향으로 활용해 매칭된 키워드로부터 파생된 교정 후보까지 끌어오도록 보강. 같은 예문 기준 매칭 0건 → 3건으로 개선.

**실측 재검증(2026-08-23)**: 시드 문구를 그대로 안 쓴 자연스러운 문장 10개(위험 8개 + 안전 2개, 진단/복약/트리아지/정신건강/임산부/광고효능 등)로 `judge_correction_candidates` 직접 호출.

| 위험 문장(8개) | 결과 |
|---|---|
| 매칭됨 (4건) | 전부 문장 안에 `혈당`/`혈압`/`스트레스`/`검사`/`건강` 같은 **키워드 단어가 우연히 같이 들어간 경우** |
| **매칭 안 됨 (4건)** | 문장에 68개 키워드 중 **단 하나도 안 걸린** 경우 — 100% 놓침 |

놓친 4건: **복약지도**("약 시간표를 짜드려요"), **위험도 분류/트리아지**("위험 단계인지 나눠서 알려줍니다"), **정신건강 상담**("마음 상태를 짚어드리고 조언"), **임산부 모니터링**("이상 신호 보이면 안내") — 전부 실제로 위험한 기능인데 키워드 단어가 하나도 안 걸려서 규칙 기반으로는 원천적으로 못 잡음. 안전한 대조군 2개(단순 걸음수 기록, 물마시기 알림)는 정확히 0건으로 나와 오탐은 없었음.

**결론**: 지금 규칙 기반은 "우연히 키워드 단어가 같이 언급된 경우"에만 recall이 개선된 것이고, **키워드 단어 자체가 아예 없는 파라프레이즈는 여전히 100% 놓침**. `correction_candidates.candidates == []`가 나왔을 때 "위험 표현이 진짜 없다"와 "표현은 있는데 규칙이 못 잡았다"를 구분할 방법이 지금은 없음.

→ **제안대로 폴백 방식 권장**: `judge_correction_candidates`가 0건을 반환할 때만 LLM①을 추가로 호출. 항상 병렬 호출하는 원래 설계보다 훨씬 저렴하고, 위 재검증 결과상 대부분의 실제 서비스 설명(데이터 종류를 자연스럽게 언급하게 되는 문장들)은 이미 규칙 기반으로 걸릴 가능성이 높아 폴백 호출 빈도 자체는 낮을 것으로 예상됨.

**LLM①과 헷갈리면 안 되는 별개 항목**: `advertising_score`(광고표현위험)는 §6.2에서 애초에 "3축 중 유일하게 LLM 판단 영역으로 설계"됐고 지금도 규칙 기반 대안이 없다고 명시돼 있음(`판정엔진_개발설계서.md:455`). 이번 재검증에서도 광고성 문장 2개 모두 "혈압"/"스트레스" 키워드 덕에 우연히 걸렸을 뿐 — 효능 주장 자체를 규칙이 이해한 게 아니라서, 광고표현위험 축은 여전히 LLM이 필요한 영역으로 남음.

## D. 테이블 자체가 없는 것 — **3개 신규 구축 진행 결정**

`판정엔진_개발설계서.md` §15에 "★ 신규 구축 필요"로 표시돼 있던 항목. `app/db/models/__init__.py` 전체를 확인해도 아래 4개는 흔적조차 없음(마이그레이션 자체가 안 됨).

| 테이블 | 컬럼 | 쓰이는 곳 | 규모/소요 | 상태 |
|---|---|---|---|---|
| `section_link_rules` | rule_id / condition_type(data_type\|service_type\|gate_verdict) / condition_value / target_section / message | 데이터확보 🔗 타 섹션 연결 안내 | **5~10행 · 1~2시간** — 설계서가 "가성비 최고"라 명시 | ✅ **완료**(2026-08-23) — 모델·마이그레이션·시드 8행·`evaluate.py` 연동까지 끝남 |
| `service_law_map` | service_type(PK) / applicable_laws(JSON) / description | 규제위험도 판단근거③ | 4행 · 반나절 | **진행** — ⚠️ `service_type` 값이 `competitors`·세션 입력폼과 문자열 완전히 일치해야 함 |
| `standard_scales` | scale_id / name·full_name / category_1 / item_count·scoring_range / license_type / source_url | 데이터확보 판단근거② | 10~20행 · 1~2일 | **진행** — ⚠️ 라이선스 확인 필수(상업적 사용 시 비용 발생하는 임상 척도 있음) |
| `app_store_ranking` | — | 시장현실성 국내수요 판단근거① | 배치 수집 개발 필요 | **보류 유지** — 팀이 이미 "유료 API·비공식 수집 이슈"로 보류 결정(`구현_현황_정리.md`) |

세 테이블 다 만들고 끝이 아니라 **조회 API도 같이 추가해야** 리포트에 반영됨 — A그룹처럼 "테이블만 있고 안 쓰임" 상태로 남지 않도록 마이그레이션+시드+조회 함수를 한 세트로 처리.
